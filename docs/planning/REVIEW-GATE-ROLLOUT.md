See [the current delegated procedure](AUTONOMOUS-DEVELOPMENT.md), which records the maintainer's later decision to set native approvals to zero while retaining procedural review. **Do not activate the unverified trusted gate.** See [the approved policy](AUTONOMOUS-DEVELOPMENT.md) and [issue #21](https://github.com/frontspan/frontspan/issues/21) for the decision and live evidence.

## Historical verified starting settings

GitHub's branch-rules API and ruleset [28263995](https://github.com/frontspan/frontspan/rules/28263995) report an active ruleset for `main`, no bypass actors, strict up-to-date status checks, `Workspace and consumer smoke` bound to GitHub Actions App `15368`, one human approval, stale approval dismissal, last-push approval, required thread resolution, no force-push or deletion, and squash only. Repository native auto-merge is available but this rollout neither changes settings nor enables auto-merge on any PR. A `404` from classic branch protection does not negate the active ruleset.

The existing check name remains the aggregate required check. It succeeds only when the Node 26 workspace job and both packed consumer jobs succeed. CI checks this repository's synthetic skeleton only; Next.js, generated types, integration and e2e are not yet implemented. The `pull_request` workflow uses read-only permissions, pinned actions, and does not persist checkout credentials or share artifacts with privileged jobs. This is **not** an independent review or policy check: GitHub Actions App binding alone does not protect a PR-editable workflow.

## Evidence and trust boundary

[`scripts/review-gate/evaluate.mjs`](../../scripts/review-gate/evaluate.mjs) is an offline reference evaluator, not a GitHub App or live check. It contains no network, execution of PR code, credential handling, check publishing, merge, or issue-update operations. In a deployed control plane it would require trusted adapters to:

- Load approved issue-to-PR scope, exact allowed paths and risk, prerequisite completion, and allowed identities from protected configuration and authenticated maintainer decisions, not from PR text or author-controlled labels. Bind the complete diff to the exact candidate, include both paths for renames, and fail closed on truncation. Path classification is a minimum safeguard; trusted scope authorization must separately classify architecture, public contracts and other high-risk semantic changes even in otherwise ordinary files. Unknown scope cannot pass.
- Bind review and CI evidence to repository, PR, head, base and current test-merge candidate as applicable. Require a trusted, explicitly clean verdict under the exact protected policy revision, zero open findings, no outstanding change requests, and resolved review threads. For sensitive changes, require an authenticated maintainer approval tied to the same candidate. Do not substitute a comment, reaction, absence of findings, a generic Actions check, or a review on another SHA.
- Invalidate stale evidence and re-evaluate from fresh authenticated state before any successful check submission. Do not assume required checks on a head SHA are isolated by base or PR, or that a fresh preflight and native auto-merge are atomic. Verify GitHub accepts the approved check on the exact immutable candidate and blocks an old verdict even if the base advances while auto-merge is armed. If that cannot be enforced natively, retain the human gate and return for a maintainer decision. A future merge queue has distinct `merge_group` candidates that would require separate support.
- Retain an authenticated pre-merge decision record. Reconcile from an actual verified squash merge on protected `main`, match it to that candidate and accepted issue, then record acceptance and close idempotently. No success signal or unmerged PR may trigger closure. A consumer of the evaluator must also enforce the current native rules and trusted rollout state separately; `eligible: true` is not authority to merge.

`pnpm test` exercises synthetic positives and negatives for absent, failed, stale and wrong-source review; unresolved findings and threads; CI source, SHA, skipped and neutral; sensitive changes and stale maintainer approval; out-of-scope changes; concurrent candidate changes; and post-merge reconciliation. These tests exercise the decision logic, not GitHub enforcement or the assumptions a trusted adapter must prove.
